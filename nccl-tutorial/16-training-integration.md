# 16 从 NCCL 回到分布式训练：优化的是关键路径

## 学习目标

- 把数据、张量、流水和专家并行映射到通信语义。
- 理解 bucket、梯度就绪时刻、通信与计算重叠的因果关系。
- 分清 NCCL 微基准提升与训练 step 时间提升。

本章讨论通用机制，不绑定某个 PyTorch、Megatron 或 DeepSpeed 版本的内部实现。框架的具体调用顺序要看目标框架源码与真实时间线，不能从一个概念图推断所有系统都相同。

## 1. 数据并行：同步的是同一份参数的梯度

每张 GPU 有相同模型，处理不同样本。反向传播后得到局部梯度 `g_r`，通常需要全局梯度：

```text
g = (g_0 + g_1 + ... + g_(P-1)) / P
```

这对应 AllReduce Sum 后除以 P，或适用条件下的平均规约/框架等价处理。不要把 NCCL Sum API 本身理解为“自动平均梯度”。

如果每个 rank 的 `g_r` 是不同样本数 `n_r` 下的局部均值，正确全局样本均值应为：

```text
g = sum(n_r * g_r) / sum(n_r)
```

直接平均各 rank 的均值，只有权重相同等条件下才正确。通信完成且所有 rank 结果相同，不代表统计语义一定正确。

## 2. 为什么框架不对每个参数单独做一次 AllReduce

数万个参数分别通信会产生大量固定开销：CPU 调用、调度、kernel launch、协议启动等。将多个小梯度放进较大的连续 bucket，可以摊薄固定开销。

但把整个模型的梯度都塞进一个超大 bucket 又有问题：要等最后一个梯度产生后才能开始通信，前面很长一段时间无法重叠。

```text
小 bucket:  更早开始通信，但操作次数多，alpha 开销明显
大 bucket:  带宽利用好，但启动晚，最后通信尾巴可能很长
```

最优大小取决于梯度生成顺序、网络、GPU 计算负载、host 调度开销，不是一个跨机器通用的常量。

## 3. 手画一次反向传播的时间线

假设反向计算总共 8 ms，四个同样大小的 bucket 分别在 2、4、6、8 ms 就绪。每个 bucket 通信独立耗时 3 ms，通信按一条 stream 串行，暂时忽略资源争用：

| bucket | ready | 通信开始 | 通信完成 |
|---|---:|---:|---:|
| B0 | 2 | 2 | 5 |
| B1 | 4 | 5 | 8 |
| B2 | 6 | 8 | 11 |
| B3 | 8 | 11 | 14 |

```text
时间(ms) 0   2   4   6   8   10  12  14
计算      [----------------]
通信          [ B0 ][ B1 ][ B2 ][ B3 ]
                                    step依赖的结果齐了
```

如果到 8 ms 才开始全部通信，理想串行完成是 20 ms；现在是 14 ms。通信总量没减少，但部分通信被计算覆盖。

这里不是实测，真实并发时每个 bucket 的 3 ms 也可能因争用变长。`max(计算时间, 通信时间)` 只是特殊理想情况下的下界直觉，不能代替依赖图计算。

## 4. 为什么 NCCL 更快，训练却没更快

至少有四种原因：

1. **通信已被覆盖。** 提速的通信不在关键路径上，step 本来就在等别的计算。
2. **占用了更多 SM/HBM。** 独跑通信更快，和 GEMM 并发后计算变慢，净收益为零甚至为负。
3. **尾部是小包而不是大包。** 优化了 128 MiB 峰值，但训练最后等待的是几个 16 KiB 操作。
4. **慢的是到达时间。** 某个 rank 的数据加载或反向计算迟到，其他 rank 的 NCCL kernel 等 peer，看起来通信耗时很长。

因此时间线中一个长 NCCL kernel 不直接证明网络带宽不足。它可能包含对输入、其他 rank 或前一阶段的等待。

## 5. 梯度累积与同步频率

若连续计算 K 个 microbatch 才做一次 optimizer step，可以在语义允许、框架正确实现的前提下延后梯度同步，减少通信启动次数。

但要明确：

- 累积后的梯度如何归一化，是否与目标有效 batch 一致？
- 所有 rank 是否执行相同的同步步数与顺序？
- 禁止同步的步骤是否仍有其他 collective，如指标统计或模型内部张量并行？
- 梯度缓冲是否因延迟同步需要保留更久？

“跳过一次 AllReduce”不是纯性能开关，它改变训练依赖与可能的数学语义。不要为了跑得快在部分 rank 上单独跳过通信。

## 6. 分片：为什么 ReduceScatter 和 AllGather 很重要

传统数据并行中，每张卡都可能持有完整参数、梯度和 optimizer state。分片方案让不同 rank 负责不同片段：

```text
完整局部梯度 -> ReduceScatter -> 每卡一片全局梯度
每卡负责更新自己的参数/状态片段
需要完整参数时 -> AllGather -> 各卡暂时获得完整视图
```

这解释了为什么“训练通信”不等于“只有 AllReduce”。逻辑上 AllReduce 的两部分可能分散到训练的不同阶段，中间插入优化器计算或按层预取。

收益是每卡常驻内存下降；代价是增加对参数可用时刻、预取和缓冲生命周期的安排。不同分片级别并不都采用上述完整流程，应按框架实际策略判断。

重要的是计算**每 rank 需要拥有的数据**，不是只比较 collective 名字。参数 AllGather 可以在下一层使用前预取，过早则增加显存峰值，过晚则在关键路径停顿。

## 7. 张量并行：通信穿插在层内部

把一个大矩阵运算分到多卡后，输出可能是：

- 各 rank 持有同一输出的部分和，需要 AllReduce。
- 各 rank 持有输出的不同切片，需要 AllGather。
- 希望保持分片布局，把部分和规约后继续分散存放，需要 ReduceScatter。

例如按矩阵乘法的归约维度切分：

```text
Y = X0*W0 + X1*W1
rank0 算第一项，rank1 算第二项
若两卡都需要完整Y -> AllReduce Sum
```

张量并行的通信更接近下一层计算的直接前置条件，通常比反向梯度同步更难全部隐藏。小消息延迟和拓扑距离因此可能很重要。

## 8. 流水并行：相邻阶段传激活与梯度

不同 stage 位于不同设备组，前向发送激活，反向发送激活梯度，常见语义是 Send/Recv。

```text
前向: stage0 -> stage1 -> stage2
反向: stage0 <- stage1 <- stage2
```

关键不是背某个 NCCL 算法，而是安排 microbatch、buffer 和依赖：

- 接收是否已经提交，能与发送共同前进？
- 多个方向的 Send/Recv 是否需要 group？
- 同一个缓冲区是否会在发送尚未读取完时被下个 microbatch 覆盖？
- 各 stage 的慢速计算是否造成流水线空泡？

如果瓶颈是 stage 负载不均，单纯提高网卡带宽可能没用。

## 9. 专家并行：AlltoAll 与不等长交换

MoE 的 token 按路由结果发往不同专家：

```text
本地tokens -> 按目标专家打包 -> AlltoAll/变长交换
 -> 专家计算 -> 反向交换 -> 还原token顺序
```

它与 AllGather 不同：不是让每张卡收到所有 token，而是让指定专家收到属于自己的那部分。

路由不均会造成不同 peer 的数量不同。除了 payload，还可能需要交换 counts/offsets，执行 pack/unpack，并处理 padding、容量和负载不均衡。

当前 NCCL 有固定 per-peer count 的 `ncclAlltoAll`；复杂变长流量还需要适合的上层调度。不要因为 nccl-tests 有 AlltoAllV 测试，就假设所有框架 MoE 都直接调用某个同名原生 API。

## 10. 多种并行叠加：先画 communicator

一张 GPU 可能同时属于数据、张量、流水或专家并行组。这些 communicator 的 rank 不是同一套编号：

```text
全局8卡
TP组: [0,1] [2,3] [4,5] [6,7]
DP组示意: [0,2,4,6] [1,3,5,7]
```

同一 GPU 在 TP 组中可能是 rank 1，在 DP 组中可能是 rank 2。一次 `root=0` 的含义取决于传入的 communicator。

放置策略也影响性能：高频、低延迟的 TP 组通常希望靠近高速互连；更大粒度的 DP 可跨节点。但这只是成本指导，最终要结合机器拓扑、模型规模与网络资源。

多个 communicator 并发还会共享 SM、HBM 和 NIC。独立调优每个组的峰值，不保证合在一起最优。

## 11. 一个可信的应用调优流程

1. 记录实际 collective 的类型、尺寸分布、rank 组和调用频率。
2. 用 nccl-tests 在相同拓扑上建立独跑基线，确认系统没有明显异常。
3. 用时间线标出 bucket ready、NCCL 开始/结束、计算结束、optimizer 前置依赖。
4. 找关键路径上的等待，区分“等待 peer”与“持续搬运慢”。
5. 只改一个因素：bucket、预取时刻、CTA 资源、进程/GPU 亲和性或算法候选。
6. 同时比较 step 时间、通信时间、计算时间、显存峰值和数值正确性。
7. 多次重复，覆盖真实 batch/sequence/并行规模，保留所有 rank 的异常信息。

一个修改如果只让 busbw 上升，却令 step 时间上升，就不是当前应用的优化。

## 自测与答案

1. 四个 bucket 的通信总时间 12 ms，计算 8 ms，重叠后一定 12 ms 吗？**不一定，要看就绪时刻、依赖、串行顺序与资源争用。本章例子是 14 ms。**
2. AllReduce Sum 得到一致梯度后，是否一定对应全局样本均值？**不一定，需正确归一化，尤其注意各 rank 样本数不同。**
3. 时间线中某 rank 的 NCCL 很长，第一步应强制 Ring 吗？**不应，先看其他 rank 到达、前置计算和实际数据通路，再决定实验。**
