# 04｜集合算法：Ring 怎样收齐所有贡献

上一章说明 GPU 怎样执行 work。本章回答一个更基础的问题：**Ring 为什么能正确完成 AllReduce？**

先不研究完整调优和 Tree 的构造细节，只用一个四 rank 的小例子验证两件事：每份贡献恰好加入一次，最后每个 rank 都得到完整结果。

进阶的带宽公式、双树和候选组合见 [集合算法进阶附录](appendix/algorithms.md)。

## 1. 把问题缩成四块数据

设四个 rank 的环为：

```text
R0 → R1 → R2 → R3 → R0
```

每个 rank 的数组分成 C0、C1、C2、C3，每块两个元素：

```text
      C0        C1        C2        C3
R0  [0,1]     [2,3]     [4,5]     [6,7]
R1  [10,11]   [12,13]   [14,15]   [16,17]
R2  [20,21]   [22,23]   [24,25]   [26,27]
R3  [30,31]   [32,33]   [34,35]   [36,37]
```

规约目标不是把 C0 集中到一个地方，而是每个 rank 都得到：

```text
[60,64, 68,72, 76,80, 84,88]
```

## 2. 第一阶段：ReduceScatter

Ring 先让每个 rank 得到一个**已经包含所有贡献的块**。

采用与 `runRing` 对应的起点：环位置 r 首先发送 `C[(r-1) mod P]`。

| 轮次 | R0→R1 | R1→R2 | R2→R3 | R3→R0 |
|---|---|---|---|---|
| RS 0 | C3 | C0 | C1 | C2 |
| RS 1 | C2 | C3 | C0 | C1 |
| RS 2 | C1 | C2 | C3 | C0 |

只追 C0：

| 接收位置 | 收到的内容 | 加入本地 C0 后 | 已包含的贡献 |
|---|---|---|---|
| R2 | R1 的 `[10,11]` | `[30,32]` | `{1,2}` |
| R3 | 上一步的 `[30,32]` | `[60,63]` | `{1,2,3}` |
| R0 | 上一步的 `[60,63]` | `[60,64]` | `{0,1,2,3}` |

关键不变量是：

> 每次接收时，已有贡献集合与新收到的集合不相交，合并后集合并集继续扩大。

经过 `P-1=3` 跳，C0 恰好包含四个 rank 的贡献，完整结果落在 R0。

其他块按同样方式推进，RS 结束时：

```text
R0：Y0=[60,64]
R1：Y1=[68,72]
R2：Y2=[76,80]
R3：Y3=[84,88]
```

不同块可以交错经过各条边，不需要等 C0 完成后才处理 C1。

## 3. 第二阶段：AllGather

RS 只让每个 rank 得到一个完整块，AG 再把这些块传播给所有 rank。

C0 的路径是：

```text
R0 → R1 → R2 → R3
```

这一阶段接收后只复制，不再加入本地输入。

每个 rank 每轮新增一个完整块，再经过 `P-1=3` 轮，所有 rank 都收齐 C0～C3，得到相同输出。

因此：

```text
AllReduce = ReduceScatter + AllGather
```

在 NCCL 的设备实现里，这两个阶段在同一个工作体中衔接。边界处会把“最后规约、保存结果、开始传播”合并到一次 primitive 调用中，不需要中间退出 kernel。

## 4. 为什么 Ring 适合大消息？

设每 rank 的输入为 S 字节，分成 P 块。

每个阶段每 rank 发送 `(P-1)×S/P`，两阶段合计：

```text
2(P-1)/P × S
```

这说明：

- 带宽方向的通信量随 P 增加趋近 `2S`，不会按 `P×S` 增长。
- 但 Ring 有 `2(P-1)` 轮逻辑传递，规模越大，串行依赖越长。

所以 Ring 容易在大消息时摊薄启动成本，小消息和大规模场景则可能更依赖低延迟结构。

多 channel 可以并行利用链路，但共享的 NVLink、PCIe 或 NIC 仍会成为瓶颈，不能简单按 channel 数倍增吞吐。

## 5. Tree 改变了什么？

Ring 是长链式依赖；Tree 让部分结果在父节点汇合，再把结果向下广播。

```text
Ring：依赖长度随 rank 数近似线性增长
Tree：依赖长度随树高近似对数增长
```

Tree 的目标主要是缩短小消息传播中的等待，并不意味着一定比 Ring 的总流量更小或所有场景都更快。

NCCL 还使用双树分担数据和转发负载。第一遍只需理解“缩短依赖”和“分散压力”即可，`ncclGetDtree` 的构造留到进阶阅读。

## 6. 三个轴不要混淆

| 轴 | 决定什么 | 例子 |
|---|---|---|
| Algorithm | 数据经过谁、何时规约或复制 | Ring、Tree |
| Protocol | 分片和就绪状态怎样组织 | Simple、LL、LL128 |
| Transport | 每条 peer 连接用什么资源 | P2P、SHM、NET |

同一个 Ring 的不同边可以采用不同 transport。换成 Tree 不会自动改变协议，换成 NET 也不会改变 AllReduce 的数学语义。
